# Feature Spec: `dulwich bugreport` (support for `git bugreport`)

## Status

Draft. This document is the acceptance rubric for the feature; it intentionally
contains no implementation details (module layout, class names, helper
functions, etc.). Implementers are free to choose how to satisfy the
criteria below, subject to the repository conventions cited in
["Repository conventions to follow"](#repository-conventions-to-follow).

## Source of intent

- Upstream issue: jelmer/dulwich#1836, "Add support for git bugreport"
  (quoted in full below; this is the *only* intent for the feature — no
  additional scope should be inferred beyond it and the clarification that
  followed).

  > Add support for the `git bugreport` command to collect information for
  > bug reports.
  >
  > This command gathers system and repository information to help with
  > troubleshooting and bug reporting.
  >
  > **Common use cases:**
  > - Generate standardized bug reports
  > - Collect environment information for support
  > - Gather diagnostic data for issue reproduction

- Clarification received: dulwich's `bugreport` should replicate C git's
  *documented command-line contract* for `git bugreport` — default output
  file name and format, `--output-directory`, and `--suffix` should match
  what git documents — and the report should collect the same *kinds* of
  information git's does (system/environment information and repository
  information), as far as dulwich can provide them. `--diagnose` (the
  compressed diagnostics archive) is optional: include it only if it fits
  naturally, otherwise omit it and say so explicitly in the documentation.
  The feature should follow this repository's own conventions for how
  commands are exposed and tested.

## What is being built and why

A new `dulwich bugreport` subcommand (exposed both as a `dulwich.porcelain`
function and as a `dulwich` CLI command, per this repo's existing pattern —
see below) that:

1. Collects diagnostic information about the user's environment (Python /
   dulwich version, platform) and, when run inside a repository, about that
   repository — mirroring the *categories* of information C git's
   `git bugreport` collects, adapted to what is meaningful for a Python
   library/tool rather than a compiled C binary.
2. Writes that information to a single text file, using the same default
   file-naming scheme, output-directory option, and suffix option that C
   git documents for `git bugreport`, so that muscle memory and any tooling
   built around `git bugreport`'s file-naming convention (e.g.
   `git-bugreport-*.txt` glob patterns) continues to work against dulwich.
3. Gives the user a starting template they can fill in with reproduction
   steps, expected behavior, and actual behavior, for pasting into an issue
   report — the "standardized bug report" use case named in the issue.

The purpose (per the issue, verbatim) is to help troubleshooting and bug
reporting: generating standardized bug reports, collecting environment
information for support, and gathering diagnostic data for issue
reproduction. Nothing beyond that — this is a diagnostics/reporting
command, not a repository-repair or analysis tool.

## Command-line contract (must match C git's documented behavior)

These are the parts of the contract the clarification says must match what
git documents for `git bugreport`(1). Each is independently checkable.

1. **Command name**: the subcommand is invoked as `bugreport` (i.e.
   `dulwich bugreport ...`, or the porcelain-level equivalent
   `porcelain.bugreport(...)`).

2. **Default output file name**: when neither `-o`/`--output-directory` is
   given, the report is written into the current working directory (i.e.
   `os.getcwd()`, not the discovered repository root, matching C git) as
   `git-bugreport-<suffix>.txt`, where `<suffix>` is produced as described
   in criterion 4.

3. **`-o <path>` / `--output-directory <path>`**: when given, the report
   file (named as in criterion 2's `git-bugreport-<suffix>.txt` pattern) is
   written inside `<path>` instead of the current directory. If `<path>`
   does not exist, the command fails with a clear error rather than
   silently creating arbitrarily nested directories or writing elsewhere.

4. **`-s <format>` / `--suffix <format>`**: the suffix is generated by
   formatting `<format>` as a `strftime`-style format string against the
   current local time, exactly as C git documents. When `--suffix` is not
   given, the default format is `%Y-%m-%d-%H%M`, matching C git's
   documented default.

5. **Refusal to overwrite**: if the target report file already exists, the
   command fails with a clear error instead of silently overwriting it
   (matching C git's behavior of not clobbering an existing bug report).

6. **`--diagnose[=<mode>]` (optional for this feature)**: C git's
   compressed-diagnostics-archive option. Per the clarification, this is
   *not required*. Either:
   - it is implemented, in which case it must follow C git's documented
     flag shape (`--diagnose` alone, and `--diagnose=<mode>` with at least
     the modes C git documents, i.e. `stats` and `all`, or a clearly
     documented dulwich-appropriate subset), or
   - it is left unimplemented, in which case the command's `--help` output
     and this repository's user-facing documentation for `bugreport` must
     explicitly state that `--diagnose` is not supported, rather than
     silently accepting or silently ignoring the flag.

   A build that silently accepts `--diagnose` and does nothing, or that
   fails with an unhelpful generic argparse error, does not satisfy this
   criterion — one of the two explicit outcomes above is required.

7. **Exit status / errors**: invalid combinations of the above (e.g.
   nonexistent `--output-directory`, or a target file that already exists)
   cause a non-zero exit from the CLI command and a raised exception from
   the porcelain function, with a message that identifies the actual
   problem (not a bare traceback with no explanation).

## Report content

The report must contain, at minimum, the two categories of information the
clarification names — "system/environment information" and "repository
information" — adapted to what dulwich can actually provide:

### System / environment information (always present)

- dulwich's version (`dulwich.__version__` or equivalent).
- The Python interpreter version and implementation running dulwich.
- The operating system / platform dulwich is running on (equivalent in
  spirit to C git's `uname` section — Python's `platform` module is an
  acceptable source, since dulwich has no compiled binary or build flags
  of its own to report).

Because dulwich is a pure-Python library/tool rather than a compiled
binary, sections of C git's report that only make sense for a C binary
(compiler used to build the binary, libc version linked against, "built
from commit" info) are **not** expected to have a dulwich equivalent — see
"Explicitly out of scope" below.

### Repository information (present when run inside a repository)

When `dulwich bugreport` is run with a discoverable repository (the same
repository-discovery rules other `dulwich` commands use), the report
additionally includes repository-level diagnostic information that is
meaningful for troubleshooting, drawing on data dulwich already exposes
elsewhere (e.g. via `porcelain`/`Repo`) — at minimum:
- the repository's path,
- whether it is bare,
- which hooks are present/enabled in the repository (dulwich's analogue of
  C git's "Enabled Hooks" section — dulwich's `dulwich.hooks` machinery is
  the natural source of truth for what counts as a recognized hook here).

When `dulwich bugreport` is run *outside* any discoverable repository, the
command still succeeds and produces a report containing at least the
system/environment section, clearly noting that no repository was found —
it must not crash or require `-o`/a repository to function, matching C
git's behavior of `git bugreport` working outside a repository.

### User-fillable template section

The report includes a template section prompting the user for
reproduction steps, expected behavior, and actual behavior (or dulwich's
equivalent framing of the same three prompts), matching the spirit of C
git's report template and the issue's "generate standardized bug reports"
use case.

## Acceptance criteria (checklist)

- [ ] `dulwich bugreport` exists as a CLI subcommand and `porcelain.bugreport`
      (or equivalently-named porcelain entry point) exists as a library
      function, following this repo's existing command-exposure convention
      (see "Repository conventions to follow").
- [ ] Running `dulwich bugreport` with no arguments, in a directory with no
      repository, succeeds and writes `git-bugreport-<timestamp>.txt` into
      the current directory, where `<timestamp>` matches `%Y-%m-%d-%H%M`
      formatted against local time.
- [ ] Running `dulwich bugreport --output-directory <dir>` writes the
      report into `<dir>` using the same file-naming scheme; a
      nonexistent `<dir>` produces a clear error and no file is written
      elsewhere.
- [ ] Running `dulwich bugreport --suffix <format>` produces a report file
      whose name embeds `<format>` interpreted as a strftime string (e.g.
      a literal, non-time-format suffix like `--suffix test` produces
      `git-bugreport-test.txt`).
- [ ] Running `dulwich bugreport` twice in a row (same directory, same
      default/explicit suffix resolving to the same file name within the
      same clock minute) fails on the second run with a clear
      "file already exists" style error, rather than overwriting the first
      report.
- [ ] The generated report's system/environment section includes dulwich's
      version, the Python version, and the platform, and is human-readable
      plain text.
- [ ] Run from inside a repository, the generated report includes that
      repository's path and hook information; run outside any repository,
      the command still succeeds and the report says no repository was
      found.
- [ ] `--diagnose` either behaves per C git's documented flag shape, or is
      documented (in `--help` and user docs) as unsupported for this
      feature — one of these two, not silent acceptance/no-op and not an
      unexplained failure.
- [ ] `dulwich bugreport --help` (or equivalent) documents all supported
      options and their defaults.
- [ ] New unit tests cover: default file naming, `--output-directory`,
      `--suffix`, refusal to overwrite an existing report, behavior inside
      vs. outside a repository, and the `--diagnose` decision above —
      placed per this repo's existing test layout (see below).
- [ ] A `NEWS` entry describes the new command, per this repo's
      contribution conventions.

## Explicitly out of scope

- **`--diagnose`'s zip/compressed-archive output** is not required by this
  feature (see contract item 6). If omitted, that omission itself must be
  documented — silence is not acceptable, but a documented "not supported"
  is.
- **Compiled-binary diagnostics** that have no meaning for a pure-Python
  project: C compiler identification/flags, libc version linked against,
  "built from" commit/build metadata other than dulwich's own release
  version. Nothing in this feature should try to report on the C toolchain
  that may have built any optional native extensions dulwich uses;
  reporting dulwich's own version number is sufficient.
- **Shell detection** (C git's report includes the user's `$SHELL`). Not
  required — dulwich is invoked as a Python CLI/library across platforms
  where "the user's shell" is a much fuzzier concept than for C git; this
  is not part of the acceptance criteria and may be omitted without
  needing to be documented as a gap (unlike `--diagnose`, which the
  clarification specifically calls out).
- **Any new telemetry, network calls, or automatic issue filing.** The
  command only writes a local file; it must not upload the report, open a
  browser, or contact any external service.
- **Redaction/sanitization of collected data beyond what's inherently safe
  to include** (no secrets, tokens, or credential values are collected in
  the first place, since none of the listed information categories touch
  credential storage) — building a general-purpose secret-scrubber for the
  report is out of scope; the fix is to not collect sensitive data, not to
  scrub it after collection.
- **Changing behavior of any existing command.** This is a new, additive
  command; no existing `dulwich` porcelain function or CLI command's
  behavior should change as a side effect of this work.
- **A GUI, interactive prompt, or editor-launching flow** for filling in
  the reproduction-steps template. The template is written into the output
  file as-is for the user to edit afterward in their own editor, the same
  way C git's `git bugreport` leaves the file for manual editing rather
  than launching one itself.

## Repository conventions to follow

(For grading/review purposes — these are observable in the current
codebase, not prescriptions invented for this feature.)

- Porcelain-level functions live in `dulwich/porcelain/` (either
  `dulwich/porcelain/__init__.py` or a dedicated submodule, following how
  e.g. `worktree.py`, `notes.py`, `tag.py` are split out); CLI subcommands
  are `cmd_<name>` classes in `dulwich/cli.py`, registered in the
  `commands` dict there, and delegate to the porcelain function rather
  than reimplementing logic.
- Public functions/classes use Google-style docstrings (per
  `CONTRIBUTING.rst`).
- Tests: CLI-level behavior belongs alongside the other `*CommandTest`
  classes in `tests/cli/test_cli.py` (using the existing
  `DulwichCliTestCase` helper); porcelain-level behavior belongs alongside
  the other `*Tests` classes in `tests/porcelain/__init__.py` (using the
  existing `PorcelainTestCase` helper). New functionality must come with
  matching unit tests per `CONTRIBUTING.rst`.
- `NEWS` entries are added at the top of the current `UNRELEASED` section,
  in the repo's existing style (`* <description>. (<author>, #<issue>)`).

## Open assumption to flag to the reviewer

C git's exact documented default suffix format and the precise wording of
its report sections should be re-confirmed against the currently published
`git-bugreport(1)` man page at implementation time (this spec was authored
from documented/training knowledge of that contract without live access to
git-scm.com to re-verify it word-for-word). Any discrepancy discovered
between this document's description of C git's contract and the actual
current `git-bugreport(1)` text should be resolved in favor of the real,
current git documentation, and the acceptance criteria above updated to
match before being treated as final.
